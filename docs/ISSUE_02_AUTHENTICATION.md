### Android compatibility adjustment

The Android project (`Sprint-2/android`, read only) was inspected. Its interim auth layer
defines `RegisterRequestDto(fullName, email, password)`, `LoginRequestDto(email, password)`,
`LogoutRequestDto(refreshToken)` and `TokenResponseDto(accessToken, refreshToken)`.
Therefore **the registration field is `fullName`** (the issue text said `name`); sending `name`
is rejected with 400. The database column and the `/auth/me` response use `name`, because
Android has no current-user DTO yet. Android also sends `Authorization` on logout; the header
is accepted and ignored. Android maps 401 → invalid credentials, 409 → email registered and
400/422 → rejected input, which matches this implementation.

**Password policy (aligned in the post-review correction):** the backend rule — at least 8
characters with at least one uppercase letter, one lowercase letter and one number (max 128) — is
the shared contract. Android originally accepted any letter plus a digit (e.g. `password1`);
its registration validator and messages now apply the backend rule (§15).

**Field-name contract (verified):** registration request `fullName` (backend DTO, Swagger,
Android `RegisterRequestDto`); `/auth/me` response `name` (backend DTO, Swagger; Android has no
current-user DTO yet). The iOS client must use the same keys.

## 4. Password hashing

- `argon2` package, **Argon2id** with the library defaults: 64 MiB memory, 3 iterations,
  parallelism 4 (stored as `$argon2id$v=19$m=65536,t=3,p=4$...`). Constant-time verification is
  done by `argon2.verify`.
- One `PasswordService` is used by registration, login and the seed.
- Unknown-email logins still run one Argon2 verification against a dummy hash, so timing does
  not reveal whether the account exists (measured: ~158 ms wrong password vs ~148 ms unknown email).
- Password policy (server-side, `src/auth/password-policy.ts`): 8–128 characters, at least one
  uppercase, one lowercase letter and one digit (Unicode-aware). Passwords are not trimmed.

**argon2 version note.** `argon2@0.45.1` (latest) was tried first. Its Windows prebuilt binary
**crashes with a segmentation fault when loaded on Node 20.17** (exit code 139; it loads fine on
Node 22.23), so npm fell back to compiling from source, which failed because Visual Studio C++
build tools are not installed. `argon2@0.44.0` (same API, not deprecated, prebuilds for Windows
x64, macOS, Linux glibc and Alpine musl) loads on Node 20.17 and in the `node:24-alpine` image.
The dependency is pinned to `~0.44.0`; upgrade once every developer uses Node ≥ 22.

## 5. JWT design

| | Access token | Refresh token |
|---|---|---|
| Secret | `JWT_ACCESS_SECRET` | `JWT_REFRESH_SECRET` (must differ) |
| Algorithm | HS256 (verification restricted to HS256; `alg: none` rejected) | HS256 |
| Payload | `{ sub, role, type: "access", iat, exp }` | `{ sub, sid, type: "refresh", jti, iat, exp }` |
| Default lifetime | 15 min (`JWT_ACCESS_TTL`) | 7 days (`JWT_REFRESH_TTL`) |
| Stored in DB | never | only as an HMAC hash |

- No names, emails or other personal data in payloads.
- `type` is checked on both sides, and the secrets differ, so a refresh token is never accepted
  as an access token and vice versa (both cases verified).
- `jti` is random so two refresh tokens issued in the same second are still different (without
  it a same-second rotation could produce an identical, still-valid token).
- The access-token strategy reloads the user on every request: deactivation and role changes
  apply immediately; the `role` claim is informational only.
- A malformed `sub`/`sid` (not a UUID) is rejected as 401 before reaching PostgreSQL.

## 6. Refresh rotation and revocation

Refresh token hashing: `HMAC-SHA-256(key, token)`, where `key = HKDF-SHA-256(JWT_REFRESH_SECRET,
info "campusmeal:refresh-token-hash")`. It is deterministic (so the stored hash can be compared)
and useless without the server secret. Comparison uses `crypto.timingSafeEqual`.

`POST /auth/refresh`:

1. Verify signature, expiration (JWT) and `type === "refresh"` → else `INVALID_REFRESH_TOKEN`.
2. Load the session by `id = sid` **and** `user_id = sub`. Missing, or owned by another user →
   `INVALID_REFRESH_TOKEN` (the two cases are indistinguishable).
3. Revoked → `REFRESH_SESSION_REVOKED`; past `expires_at` → `INVALID_REFRESH_TOKEN`.
4. Presented token hash ≠ stored hash → the token was already rotated (superseded) →
   `INVALID_REFRESH_TOKEN`. The session is **not** modified; a warning with only the session and
   user UUIDs is logged. (Early rejection only — step 6 is the real guard.)
5. Inactive user → `USER_INACTIVE`.
6. Issue a new pair and rotate with one atomic compare-and-swap:
   `UPDATE refresh_sessions SET token_hash = <new>, expires_at = <new>, updated_at = now()
   WHERE id = <sid> AND user_id = <sub> AND token_hash = <presented> AND revoked_at IS NULL
   AND expires_at > now()`.
   - `affected = 1` → success, return the new pair.
   - `affected = 0` → a concurrent request rotated (or logged out) first → `INVALID_REFRESH_TOKEN`.
     The losing request **never** sets `revoked_at`, so the winner's new token stays valid.

PostgreSQL row locking makes the concurrent UPDATEs serialize: the first commits, the others
re-evaluate `token_hash = <presented>` against the new value and match 0 rows. Rotation keeps
the session row (same `sid`) and replaces its hash, so the previous token can never succeed
again, while the current token stays valid until it expires, is rotated again, is logged out,
or the user becomes inactive. Verified after the correction: 5 and 10 parallel refreshes →
exactly one 200, all others 401 `INVALID_REFRESH_TOKEN`, session not revoked, winner token → 200.

**Trade-off (prototype scope):** full token-family replay detection is not implemented. A
replayed old token gets 401, but the current session stays active; detecting theft by revoking
the session on replay would need extra state (e.g. a per-session token generation) so a
legitimate concurrent loser can be told apart from an attacker.

`POST /auth/logout`: the same checks (1–4), then `UPDATE ... SET revoked_at = now() WHERE id =
<sid> AND user_id = <sub> AND token_hash = <presented> AND revoked_at IS NULL` → 204.
**Chosen behavior:** invalid, expired, unknown or superseded tokens → 401
`INVALID_REFRESH_TOKEN` (the session is left unchanged); an already logged-out session → 401
`REFRESH_SESSION_REVOKED` (logout is not idempotent). No access token is needed. The access token
of that session keeps working until it expires (stateless, at most 15 minutes).

Registration creates the user and its first session in one database transaction.

## 8. Authorization foundation (for Issues #3–#8)

```typescript
@Auth()                    // any authenticated, active user (JwtAuthGuard + RolesGuard + Swagger bearer/401 docs)
@Auth(UserRole.ANALYST)    // analysts only; others get 403 FORBIDDEN (also documents 403)

@Get('summary')
@Auth(UserRole.ANALYST)
summary(@CurrentUser() user: AuthenticatedUser) { ... }   // or @CurrentUser('id') userId: string
```

The pieces are also usable separately: `@UseGuards(JwtAuthGuard, RolesGuard)` +
`@Roles(UserRole.ANALYST)`. `RolesGuard` allows routes without role metadata, returns 403 when
the role is missing, and fails closed (401) if used without `JwtAuthGuard`. The guards work from
any module without importing `AuthModule` (verified with a temporary module).
No analytics endpoint was created.

`JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET`, `JWT_ACCESS_TTL`, `JWT_REFRESH_TTL` are now

secret; when a TTL is not `<n><s|m|h|d>`; or when the access TTL is not shorter than the refresh
TTL. `.env.example` contains distinct placeholders that are rejected on purpose.
`DEMO_*` variables are read only by the seed. See [BACKEND_SETUP.md §3](BACKEND_SETUP.md).

## 13. Security limitations (academic prototype)

- **No rate limiting / lockout** on login, register or refresh (out of scope). Argon2 slows
  brute force but does not stop it; add throttling before any public deployment.
- **Access tokens are not revocable** before expiry (15 min). Logout ends the refresh session only.
- **No token-family replay detection**: a stolen, already-rotated refresh token only receives
  401; it does not end the victim's session (and a stolen *current* token works until rotated,
  logged out or expired). Clients should still use a single-flight refresh; a client that
  retries a refresh whose response was lost must log in again.
- **Session rows are never purged**; expired/revoked rows accumulate (no background jobs in
  scope). A later cleanup (`DELETE ... WHERE expires_at < now() - interval '30 days'`) is advised.
- **No per-user session limit** and no "log out everywhere" endpoint.
- **Registration reveals whether an email is registered** (409), as required by the contract.
- **Secret rotation** logs everyone out (refresh secret) and has no key-id/overlap support.
- The request-logging interceptor does not log requests rejected by guards (e.g. 401 on `/auth/me`),
  because Nest runs guards before interceptors (same limitation as unmatched routes in Issue #1).
- Swagger remains public; HTTPS is expected to be provided by the deployment environment.

## 15. Post-review correction: concurrent refresh (2026-09-22)

### Reproduction (before the fix, unmodified build)

1. Registered a test user and took its refresh token.
2. Sent 5 parallel `POST /auth/refresh` requests with that token.
   Result: `200 | 401 REFRESH_SESSION_REVOKED ×4` — exactly one winner.
3. Immediately refreshed with the **winner's** new token → **401 `REFRESH_SESSION_REVOKED`**.
4. Session row (flags only): `revoked: true, unexpired: true, rotated: true, hash_length: 64`.

**Root cause:** two code paths in `AuthService` treated a superseded token as theft and revoked
the whole session: (a) a loser whose compare-and-swap UPDATE matched 0 rows, and (b) a loser that
read the session after the winner committed and saw a different hash. Either one set
`revoked_at` on the session the winner had just rotated, so the winner's new token died.

### Correction (`src/auth/auth.service.ts`)

- Removed revoke-on-reuse (`revokeAfterReuse`). A superseded token — hash mismatch or a lost
  compare-and-swap — now returns `401 INVALID_REFRESH_TOKEN` and never writes to the session. Only
  IDs are logged (`Rejected superseded refresh token for session … of user …`).
- The atomic UPDATE is unchanged in spirit and now also matches `user_id`; logout's UPDATE
  matches `user_id` too, and a lost logout race returns `INVALID_REFRESH_TOKEN`.
- `INVALID_REFRESH_TOKEN` message: "The refresh token is invalid, expired or already used".
- Swagger description of `/auth/refresh` updated. No schema change, no new migration.
